# Справка администратора: Управление освещением

> Спецификация фичи (`specs/Управление освещением.md`) в проекте не найдена, активной
> задачи в task-gate тоже нет. Документ составлен по фактическому коду и README —
> разделы, которые в спецификации обычно берутся из бизнес-контекста/guardrails/HITL-карты,
> явно помечены как отсутствующие, а не выдуманы.

## Назначение

Демонстрационный клиент-серверный проект «Фонарь» (LanternServer / LanternClient).
Сервер раз в 10 секунд генерирует случайную команду управления освещением (`ON`, `OFF`,
`COLOR` или намеренно нераспознаваемую `UNDEFINED`) и передаёт её клиенту по протоколу
TLV8 через обычный TCP-сокет. Клиент декодирует команду и пишет в лог, как он на неё
реагирует. Физического устройства и визуального интерфейса нет — это симуляция
протокола обмена командами.

## Требования к окружению

- Стек: Python 3.10+ (в `.venv` каждого приложения зафиксирован Python 3.10.0),
  `asyncio` + `aiohttp`.
- Зависимости: `aiohttp==3.9.5`, `tlv8==0.10.0` (`requirements.txt`); для тестов —
  `pytest==8.3.3` (`requirements-dev.txt`).
- Переменные окружения и секреты не используются — вся конфигурация только через
  `config.ini`.

## Установка и развёртывание

- Базы данных и миграций нет.
- Helm-чартов, K8s-манифестов и шагов Azure Pipelines в проекте нет — это обычный
  локальный Python-процесс.
- Установка и запуск (отдельно для «Сервер» и «Клиент»):

  ```
  pip install -r requirements.txt
  python LanternServer.py   # в папке "Сервер"
  python LanternClient.py   # в папке "Клиент"
  ```

## Конфигурация

- **Сервер** (`Сервер/config.ini`):
  - `[DEFAULT] port` — порт собственного aiohttp-сервера (сейчас `9997`); маршрутов у
    него сейчас нет, это зарезервированная точка расширения (например, под будущий
    health-check).
  - `[SERVER] host`/`port` — адрес TCP-сокета, на котором сервер принимает подключение
    клиента и рассылает команды (`127.0.0.1:9999`).
- **Клиент** (`Клиент/config.ini`):
  - `[DEFAULT] port` — порт собственного aiohttp-сервера клиента (`9998`), тоже без
    маршрутов.
  - `[SERVER] host`/`port` — адрес сервера, к которому клиент подключается (`127.0.0.1:9999`).
- **Набор команд** задаётся файлом `commands` (JSON) в каждой папке — по одному коду
  (`type`, hex) и длине полезной нагрузки (`length`) на команду: `ON` (`0x12`, 0),
  `OFF` (`0x13`, 0), `COLOR` (`0x13`, 20), `UNDEFINED` (`0x55`, 50). Файлы `commands` у
  клиента и сервера должны быть идентичны — если они расходятся, команды перестают
  распознаваться на стороне клиента.
- Feature flags и списки разрешённых внешних хостов не применяются: вся связь идёт
  между локальными процессами (сейчас на `127.0.0.1`), исходящих запросов во внешние
  системы фича не делает.

## Работа с ПДн

Не применимо. Спецификация с флагом `pdn_impact.affected` отсутствует, но по коду

процесса, а не идентификатор человека).

## Мониторинг и диагностика

- Логи пишутся одновременно в консоль (UTF-8, чтобы кириллица не искажалась на Windows)
  и во вращаемый файл `server.log` / `client.log` в папке приложения (до 1 МБ, 3
  бэкапа). Настройка вынесена в класс `AppLogger` (`logger.py`).
- Что логируется: запуск сервиса, ожидание/установление TCP-подключения, каждая
  отправленная (сервер) или полученная (клиент) команда, реакция клиента на команду,
  разрывы соединения и попытки переподключения.
- Типичные сообщения:
  - «Не удалось подключиться к серверу» / «Ошибка при приёме подключения» — сеть или
    порт недоступны; сервис сам повторяет попытку каждые 5 секунд.
  - «Клиент отключился» / «Соединение с сервером потеряно» — обрыв TCP-соединения;
    сервис переходит в режим ожидания нового подключения без падения процесса.
